# Модульный монолит на Java для BuildMate

## Контекст и постановка задачи

BuildMate должен предоставлять веб-интерфейс, каталог, подбор совместимых комплектующих, учётные записи и почтовые уведомления. SRS задаёт Java 21 и один экземпляр приложения с одной базой данных, но не требует микросервисов. Нужно выбрать разбиение, которое позволит независимо проверять правила совместимости и подбор, сохранив простое развёртывание.

Как организовать приложение, чтобы основные функции имели ясные границы, а проект оставался посильным для учебной команды?

## Драйверы решения

- Java 21 и одна база данных (REQ-BUILD-001, REQ-INT-003).
- Модуль подбора и совместимости не зависит от веб-слоя и БД (REQ-MAINT-001).
- Один экземпляр приложения и один PostgreSQL (SRS, раздел 3.5.3).
- Ограниченные сроки и ресурсы учебного проекта.

## Рассмотренные варианты

- Однослойное приложение без внутренних границ.
- Модульный монолит: веб-, прикладной, доменный и инфраструктурный слои в одном приложении.
- Микросервисы с отдельным развёртыванием каталога, подбора, учётных записей и уведомлений.

## Итог решения

Предлагается модульный монолит на Java 21. Это согласуется с ограничением на один экземпляр, позволяет тестировать доменную логику без веб-интерфейса и не добавляет сетевую координацию между сервисами. Решение пока предложено и должно быть подтверждено заказчиком.

### Последствия

- Хорошо: одна сборка и один процесс развёртывания.
- Хорошо: правила совместимости можно тестировать независимо от HTTP и БД.
- Плохо: общий процесс означает, что ресурсоёмкий подбор и фоновые задачи делят ресурсы с веб-запросами.
- Нейтрально: при росте нагрузки модули можно выделить позднее, но это потребует отдельного решения и изменения архитектуры.

### Подтверждение

Проверить структуру зависимостей на ревью и убедиться, что модуль совместимости не импортирует веб-слой или конкретные адаптеры БД. Ключевые правила должны иметь модульные тесты согласно REQ-MAINT-001.

## Плюсы и минусы вариантов

### Однослойное приложение

- Хорошо, потому что минимум начальной структуры.
- Плохо, потому что логика подбора легко связывается с HTTP и хранением, а требование модульности становится сложнее проверить.

### Модульный монолит

- Хорошо, потому что балансирует простоту развёртывания и разделение ответственности.
- Плохо, потому что границы модулей нужно поддерживать дисциплиной и ревью.

### Микросервисы

- Хорошо, потому что модули можно независимо развёртывать и масштабировать.
- Плохо, потому что добавляются сетевые контракты, распределённая диагностика и согласование данных, не требуемые текущим SRS.

## Дополнительная информация

Связанные требования: REQ-MAINT-001, REQ-BUILD-001, REQ-INST-001. Проектные элементы: SDD, раздел 3.2 и 3.5. Пересмотреть при необходимости нескольких экземпляров приложения или независимого масштабирования подбора.
